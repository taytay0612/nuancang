# 实现过程与经验

记录从单文件网页到三形态系统的过程，以及每一步的判断依据。文中结论都来自实测响应或日志，不是推测。

## 一、起点

储藏室物理条件已定：5 个柜位、56 个箱子、层板方案已出 PDF 和清单。缺的是数字档案：箱子在哪、装了什么、怎么快速找到。

第一版是单文件网页（v1.0）：`localStorage` 存整份 JSON，平面图用 SVG 画，标签用 Canvas 生成 Code 128。能打印，但只有一个浏览器能看到。

## 二、云端化走过的四条路

### 1. Supabase 建表 + 前端直连

建了 `public.nuancang_spaces`，一个账号一行，整份数据放 `data jsonb`。

用公开密钥探测时返回 `42501 permission denied`，提示 `GRANT SELECT ... TO anon`。结论：表建好了，授权没配全。后续补了 `supabase_setup.sql`，只给 `authenticated` 授权，`anon` 一律收回。

### 2. iframe 桥接（放弃）

早期方案是入口页用 iframe 装原应用，外层做登录和 `localStorage` 双向同步。放弃原因：同源要求让部署变复杂，且同步层要猜应用内部的数据键；应用一升级，桥就断。

改为同一页面内做存储适配器：`localStorage` / `/api/state` / Supabase 三选一，界面层完全不用改。

### 3. Supabase Storage 托管网页（失败）

把 `index.html` 传进公开桶，访问返回：

```
content-type: text/plain
content-security-policy: default-src 'none'; sandbox
x-content-type-options: nosniff
```

浏览器只显示源码。这是平台防钓鱼策略，改不了。

### 4. Supabase Edge Function 转发（失败）

写函数从 Storage 取页面，用 `text/html` 返回。函数确实跑起来了（`x-served-by: supabase-edge-runtime`），但响应头仍被网关改写：

```
content-type: text/plain
content-security-policy: default-src 'none'; sandbox
```

函数里设的 `text/html` 被覆盖。结论：`*.supabase.co` 不允许渲染 HTML，两条路都堵死。

## 三、Netlify 托管

静态站拖拽部署，坑集中在"发布"这一步：

| 现象 | 原因 | 处理 |
|---|---|---|
| 401 `Password protected site` | Drop 站点未认领，平台加了临时密码 | 登录状态重新拖一次，或认领站点 |
| 404 `Site not found` | 站点仍是"仅团队可见" | 点 `Make public` |
| 页面没变化 | 拖拽成 Draft 部署，未发布 | 部署后点 `Publish deploy` |
| `_redirects` 不生效 | 文件结尾缺换行，Netlify 整份忽略 | 末尾补 `\n` |

## 四、手机连不上 Supabase

电脑能登录，手机 Wi-Fi 登录失败，切流量成功。说明手机那条网络到 `supabase.co` 不通，与账号和代码无关。

解法：页面不再直连 Supabase，改走同域反代。

```
浏览器 → https://<site>.netlify.app/sb/* → Netlify → Supabase
```

`_redirects` 一行搞定，不需要函数：

```
/sb/*  https://<project-ref>.supabase.co/:splat  200
```

前端把 `CLOUD_URL` 改成 `location.origin + '/sb'`，登录、读写全部同域，跨域预检也省了。

验证方式：`/sb/auth/v1/health` 返回 Supabase 的 `No API key found`，说明请求确实到了 Supabase，而不是 Netlify 的 404。

## 五、代码层的坑

| 现象 | 根因 | 修复 |
|---|---|---|
| 登录成功但一直"本机暂存" | 改用原生 `fetch` 后删了 `cloudClient`，读取函数仍在引用，抛 `ReferenceError` | 去掉该判断，只检查 `cloudSession` |
| 保存失败没有任何提示 | `pushState` 的 catch 只改状态不弹提示 | 首次错误弹 toast，成功后清空 |
| 登录页按钮点了没反应 | 依赖 GitHub OAuth，而 GitHub 直连被重置，按钮脚本加载不全 | 改邮箱密码为主路径，GitHub 降级为备选 |

## 六、经验

1. **先探服务端事实，再改前端**。`42501`、`text/plain`、`401` 这些响应头比任何猜测都快。一次 `curl` 或页面探针，能省掉几轮试错。
2. **平台的"免费托管"常带小动作**：未认领的密码页、Draft 部署、注入的徽标 iframe。判断依据要看响应头与 DOM，不看页面长得对不对。
3. **错误必须可见**。同一个"本机暂存"背后可能是网络、授权、代码异常三种原因。把 `err.message` 弹出来，定位时间从小时降到分钟。
4. **CDN 依赖是国内项目的隐形炸弹**。去掉 `supabase-js` 的 CDN，改用原生 `fetch` 调接口，页面再无外部脚本依赖。
5. **同域反代是绕开跨境域名问题的最短路径**。一行 `_redirects`，不用函数、不用额外账号。
6. **静态包要有可核对的标识**。文件大小、修改时间、SHA256 前 16 位写进对话，避免"传了但没生效"的扯皮。
